# AI 友好官网模板建设规范

## 1. 文档目的

本文用于指导 GEOFlow 官网模板、AI 建站模板、企业官网主题与页面模块的设计、生成、改造和验收。

AI 友好官网模板的目标，不只是让页面“像官网”，而是让搜索引擎、AI 搜索、问答模型和抓取程序能够稳定理解：

- 这个网站属于谁；
- 这个品牌或公司做什么；
- 提供哪些产品、服务或解决方案；
- 能回答用户哪些真实问题；
- 哪些信息来自企业官方事实；
- 页面之间如何互相支撑；
- 页面是否可索引、可引用、可更新、可复测。

核心原则：

> 官网模板要交付正文、事实、关系、证据和更新信号。视觉是表达层，结构化数据是辅助层，HTML 正文才是 AI 和搜索系统最稳定的理解入口。

## 2. 官网 GEO 的建设目标

参考外部课程资料《官网做 GEO 的逻辑拆解》，官网 GEO 不应被理解为“在官网里加关键词”或“把页面写得更像营销页”。更合适的理解是：

官网要成为 AI 能稳定访问、理解和引用的企业事实系统。

因此，AI 友好官网模板需要同时解决四件事：

| 系统 | 要解决的问题 | 模板建设要求 |
| --- | --- | --- |
| 企业事实系统 | AI 是否知道企业是谁、做什么、提供什么 | 页面必须输出稳定的品牌介绍、产品服务、适用对象、联系信息 |
| 问题覆盖系统 | AI 是否能在用户提问时匹配到官网内容 | 模板要预留问题页、FAQ、文章、专题和解决方案入口 |
| 页面表达系统 | AI 是否能从 HTML 正文中抽取答案 | 关键信息必须是可读正文，不依赖图片、Canvas、SVG 或异步脚本 |
| 访问测量系统 | AI 与搜索是否能持续抓取和更新 | 保留 canonical、sitemap、时间、内链、状态码和日志测量能力 |

模板建设的终点不是“页面上线”，而是形成一个可持续维护的官网内容系统。

## 3. AI 友好官网的交付物

AI 友好官网模板至少要交付三类内容。

| 类型 | 要求 | 说明 |
| --- | --- | --- |
| 正文 | 关键答案直接存在于 HTML 正文中 | 不能只放在图片、轮播图、动效、Canvas、SVG 或异步 JS 中 |
| 关系 | 用语义结构和内链说明内容关系 | 品牌、产品、服务、文章、FAQ、案例、联系页面之间要互相关联 |
| 更新信号 | canonical、sitemap、时间、状态码清晰 | 让搜索引擎和 AI 判断页面是否可靠、是否最新 |

Schema 只能表达页面中真实存在的内容，不能替代正文，更不能扩写页面没有出现的业务承诺。

## 4. 页面语义结构标准

每个官网页面都应使用清晰的 HTML 语义骨架。

推荐结构：

```html
<header>
  品牌 Logo、主导航、搜索入口、联系入口
</header>

<main>
  <article>
    <h1>页面核心主题</h1>
    <p>直接说明页面要回答的问题，或给出品牌/产品的核心介绍。</p>

    <section>
      <h2>事实说明</h2>
      <p>说明企业、产品、服务对象、能力边界和官方信息。</p>
    </section>

    <section>
      <h2>证据与关联内容</h2>
      <p>关联文章、分类、案例、FAQ、联系方式或其他可验证内容。</p>
    </section>
  </article>
</main>

<footer>
  联系方式、公司地址、官网备注、版权、备案、重要页面入口
</footer>
```

不建议：

- 首屏只有口号，没有说明品牌是做什么的；
- 核心内容只存在于轮播图、背景图、Canvas、SVG 或 JS 渲染结果中；
- 大量使用“领先、专业、赋能、智能化”等空泛词，但没有明确对象、场景和证据；
- Schema 写了 `Product`、`Service` 或 `FAQPage`，但页面正文没有对应内容；
- 模板里保留演示客户、虚构指标、假案例或无法提交的占位表单。

### 4.1 前台文案中性化标准

官网前台面对的是访客和抓取程序，不应暴露建站过程、系统实现或数据来源说明。模板可以在内部文档、后台说明、manifest 或注释中记录字段来源，但公开页面文案必须保持中性、自然、官网化。

公开页面禁止出现这类说明：

- “系统配置”“后台设置”“本模块读取”“数据来源”“模板编号”“AI 友好模板”；
- “请在后台配置”“配置后自动同步”“站点设置会自动更新”；
- “缺少配置时不自动生成”“不输出占位数据”等实现说明；
- 面向开发或运营人员的字段解释、模块说明、测试说明。

中性栏目标签可以使用中文或英文，例如“Brand profile”“Brand summary”“Content topics”“Featured articles”“Contact”。是否使用英文取决于主题视觉风格。若主题本身采用英文小标签 + 中文标题的视觉语言，应保持同类标签一致，而不是只局部使用英文。

推荐表达方式：

| 场景 | 不建议前台展示 | 推荐前台展示 |
| --- | --- | --- |
| 品牌介绍为空 | 请在后台网站设置中填写网站描述 | 暂无品牌简介 |
| 联系方式为空 | 后台暂未配置联系方式 | 暂无联系方式 |
| 文章为空 | 发布文章并设置为精选后会展示 | 暂无精选内容 |
| 分类为空 | 后台创建分类后自动生成入口 | 暂无内容分类 |
| 模块说明 | 本模块读取后台网站名称和官网备注 | Brand profile / Content topics / Featured articles / Contact |

前台文案应像真实官网在对访客说话，而不是像系统在向管理员解释数据怎么来的。

## 5. 首页模板标准

首页必须回答 AI 最关心的几个问题：

- 这个网站属于谁；
- 这个品牌或公司做什么；
- 提供哪些产品、服务或解决方案；
- 适合哪些客户、行业或场景；
- 有哪些可验证内容；
- 如何联系；
- 内容是否持续更新。

### 5.1 品牌首屏

要求：

- `h1` 使用品牌名称或品牌名称 + 核心定位；
- 首屏正文直接说明品牌做什么；
- 副标题、描述优先读取后台网站设置；
- 如果有后台首页轮播图，可以用于视觉展示，但不能替代正文；
- CTA 指向真实页面，例如“联系我们”“查看文章”“了解服务”“查看案例”。

### 5.2 品牌介绍

要求：

- 简明介绍公司、产品、行业、服务对象；
- 使用后台真实数据或企业真实资料；
- 不写虚构客户、虚构指标、演示数据；
- 如果系统还没有独立公司介绍字段，可临时使用网站描述和官网备注，但模板要为后续扩展预留结构。

### 5.3 产品 / 服务模块

产品和服务是官网 GEO 的核心事实。模板应为每个产品或服务预留独立结构。

建议字段：

- 产品或服务名称；
- 一句话摘要；
- 详细介绍；
- 适用对象；
- 核心能力；
- 解决的问题；
- 相关文章或 FAQ；
- 详情入口或联系入口。

如果当前系统没有产品配置入口，模板不应编造产品。可以隐藏模块，或展示真实空状态，并在规范中保留字段设计。

### 5.4 解决方案模块

解决方案可以按行业、场景、客户需求或问题类型组织。

每个方案应说明：

- 适合谁；
- 解决什么问题；
- 如何交付；
- 关联哪些产品、服务、文章、案例或 FAQ；
- 有什么前置条件或能力边界。

### 5.5 问题覆盖与 FAQ 模块

AI 搜索的入口通常是问题，而不是栏目名。模板应预留问题覆盖模块。

要求：

- 问题和答案必须在页面正文可见；
- 问题应来自真实业务咨询、客服问题、搜索词、品牌诊断问题或文章主题；
- 每个答案要直接、明确，避免只写营销口号；
- FAQ Schema 的问题与答案必须和正文一致；
- 同一问题可以链接到更详细的文章或产品页。

建议问题类型：

- 品牌是谁；
- 产品是什么；
- 适合谁；
- 和竞品有什么不同；
- 如何购买或联系；
- 有哪些限制；
- 是否支持某个行业、地区、平台或场景。

### 5.6 内容与文章模块

要求：

- 接入系统真实文章；
- 首页展示精选文章、最新文章、热门文章、分类入口；
- 文章标题、摘要、发布时间、分类和链接必须存在于 HTML 中；
- 文章为空时展示真实空状态，不生成演示资源卡；
- 文章应能覆盖用户问题，而不是只发布新闻稿。

### 5.7 联系我们模块

要求：

- 接入后台配置的联系方式、公司地址、官网备注；
- 提供联系页链接；
- 如果系统没有表单能力，不放占位表单；
- 二维码、账号、邮箱、电话等都要有清晰文本说明；
- 联系信息为空时展示真实空状态；
- 前台空状态使用“暂无联系方式”等中性表达，不提示访客去后台配置。

### 5.8 页脚

页脚必须使用系统真实数据。

建议包含：

- 网站名称；
- 官网备注；
- 联系方式；
- 公司地址；
- 备案信息；
- copyright；
- 重要页面链接；
- 分类或文章入口。

页脚不应使用网站描述代替官网备注。

## 6. 内容事实标准

AI 友好官网需要一套稳定的事实层。模板在生成或渲染内容时，应遵守以下标准：

- 明确主体：公司/品牌名称必须可见；
- 明确业务：用一句话说明“做什么”；
- 明确对象：说明服务哪些客户、行业或场景；
- 明确产品：产品或服务不要只写抽象能力；
- 明确边界：不能承诺未配置、未提供、无法验证的能力；
- 明确证据：用文章、案例、FAQ、官方链接、联系方式支撑；
- 明确更新时间：文章、案例、报告等内容应输出时间信号。

不确定的信息不要写成确定事实。没有数据时显示空状态，而不是造数。

## 7. 页面类型标准

### 7.1 首页

首页负责建立品牌主体和内容入口。

必须包含：

- 唯一 H1；
- 品牌介绍正文；
- 产品/服务或内容方向；
- 文章或分类入口；
- 联系入口；
- canonical；
- WebSite / Organization Schema。

### 7.2 关于页

关于页负责说明企业身份。

必须包含：

- 公司或品牌介绍；
- 业务范围；
- 服务对象；
- 联系方式或联系页入口；
- Organization 或 AboutPage Schema。

不应固定写成系统项目介绍。模板必须读取当前站点数据。

### 7.3 联系页

联系页负责承载真实联系信息。

必须包含：

- 联系方式；
- 公司地址；
- 官网备注；
- 补充二维码或账号信息；
- ContactPage Schema。

没有联系方式时，前台展示中性空状态；管理端或内部检查说明可以提示后台配置，但不要生成假表单。

前台页面应显示中性空状态，例如“暂无联系方式”。“后台配置”提示只应出现在管理端、内部文档或检查清单中。

### 7.4 分类页

分类页负责组织某一类主题。

必须包含：

- 分类名称作为 H1；
- 分类描述；
- 文章列表；
- 分页；
- canonical；
- CollectionPage Schema。

分类描述为空时不编造描述。

### 7.5 文章页

文章页负责回答具体问题或承载深度内容。

必须包含：

- 文章标题 H1；
- 摘要；
- 正文 HTML；
- 作者、分类、发布时间、更新时间；
- 相关文章；
- Article Schema；
- 可读的目录或锚点结构。

文章正文不能只依赖图片或附件。

### 7.6 产品 / 服务页（建议扩展）

如果系统新增产品配置，应提供独立产品或服务页。

必须包含：

- 产品/服务名称；
- 核心介绍；
- 适用对象；
- 功能或服务范围；
- 解决的问题；
- 价格、交付方式或联系入口；
- FAQ；
- Product 或 Service Schema。

### 7.7 案例页（建议扩展）

如果系统提供案例库，应将案例页作为可验证证据。

必须包含：

- 案例主体；
- 行业或地区；
- 使用的产品/服务；
- 问题背景；
- 过程说明；
- 结果说明；
- 相关内容入口。

如果案例数据为系统批量生成或样例数据，不能写成真实客户背书。

## 8. Schema 结构化数据标准

Schema 只用于表达页面真实存在的内容。

推荐按页面类型输出：

| 页面 | 推荐 Schema |
| --- | --- |
| 全站布局 | `WebSite`, `Organization` |
| 首页 | `WebSite`, `Organization` |
| 关于页 | `AboutPage`, `Organization` |
| 联系页 | `ContactPage`, `Organization` |
| 分类页 / 列表页 | `CollectionPage`, `ItemList` |
| 文章页 | `Article`, `BreadcrumbList` |
| FAQ 模块 | `FAQPage` |
| 产品页 | `Product` 或 `Service` |
| 案例页 | 优先 `Article`，有明确案例结构时再扩展 |

基本要求：

- Schema 的名称、描述、URL 要与页面正文一致；
- `url` 使用 canonical URL；
- `datePublished`、`dateModified` 必须来自真实数据；
- FAQ Schema 的问题和答案必须在页面正文可见；
- 不要把虚构客户、虚构指标、演示数据写入 Schema；
- 不要用 Schema 扩写页面没有出现的业务能力。

## 9. Sitemap 与可访问性

AI 友好官网必须提供清晰地图。

建议 sitemap 覆盖：

- `/`
- `/about`
- `/contact`
- `/news`
- `/category/{slug}`
- `/article/{slug}`
- `/archive`
- `/product/{slug}`，如果系统存在产品页；
- `/case/{slug}`，如果系统存在案例页。

要求：

- sitemap URL 与 canonical 保持一致；
- 已删除或隐藏页面不要继续留在 sitemap；
- 重要页面应可从导航、首页或页脚进入；
- 页面关闭 JS 后，核心正文仍应可读；
- 图片必须有 alt，但图片不能替代正文。

## 10. 本系统官网模板默认数据集

官网模板建设时，应默认预留本系统已经具备的数据集。模板可以不使用所有字段，但不应把已有系统数据写死为静态文案。

### 10.1 数据集总览

| 数据集 | 来源 | 典型用途 |
| --- | --- | --- |
| 站点基础信息 | 后台网站设置、`SiteSettingsBag`、全局布局变量 | Logo、网站名称、首屏标题、SEO、页脚 |
| SEO 与规范化信息 | 页面控制器、`site.partials.seo-head` | title、description、keywords、canonical、OG 信息 |
| 导航分类 | `Category` 表、全局 `$navCategories` | 主导航、页脚导航、分类入口 |
| 首页文章数据 | `HomeController` | 精选文章、热门文章、最新文章、搜索结果 |
| 分类页数据 | `CategoryController` | 分类标题、分类描述、分类文章列表 |
| 文章详情数据 | `ArticleController` | 文章正文、摘要、标签、相关文章、Schema |
| 联系我们数据 | 后台网站设置、`PageController::contact`、全局布局变量 | 联系模块、联系页、页脚联系区 |
| 首页轮播图 | 后台网站设置 `home_carousel_slides` | 首屏辅助视觉、轮播图区域 |
| 页脚与备案 | 后台网站设置、`site.partials.footer-filing` | 版权、官网备注、备案链接、联系信息 |
| 归档数据 | `ArchiveController` | 文章归档页、年月归档链接 |
| 公司介绍（建议扩展） | 建议新增到后台网站设置 | 首页品牌介绍、关于页、Organization Schema |
| 产品 / 服务介绍（建议扩展） | 建议新增到后台网站设置 | 首页产品服务模块、Product/Service Schema |
| FAQ / 问题库（建议扩展） | 建议新增到后台内容或网站设置 | FAQ 模块、问题覆盖、FAQPage Schema |
| 案例库（已有或建议扩展） | 产品案例库 / 案例数据表 | 可信证据、行业场景、案例页 |

## 11. 模块插件建设规范

如果后续支持“模块插件 + 拖拽编排 + 保存为模板”，每个模块都必须定义清楚：

| 项目 | 要求 |
| --- | --- |
| 模块名称 | 清楚说明模块用途，例如品牌介绍、产品服务、FAQ、文章列表 |
| 数据来源 | 标明读取哪个系统字段、表或配置 |
| 正文输出 | 核心内容必须输出为 HTML 正文 |
| 空状态 | 缺少数据时显示什么，不允许自动造内容 |
| 内链策略 | 该模块应链接到哪些页面 |
| Schema 策略 | 是否输出 Schema，输出哪些字段 |
| 可复用性 | 是否可保存为模板、是否支持排序和启停 |
| 验收规则 | 如何判断模块内容可被 AI 抓取和引用 |

模块不是纯视觉积木。每个模块都要回答“它给 AI 增加了什么事实或关系”。

## 12. AI 模板生成提示词

可用于 AI 建站模板生成：

```text
生成一个 AI 友好的企业官网模板。

页面必须使用语义化 HTML，正文内容优先，Schema 只表达页面真实存在的内容。

禁止生成虚构客户、虚构指标、演示数据、假案例和不可提交的占位表单。

首页需要接入网站名称、副标题、描述、公司介绍、产品/服务介绍、FAQ、文章、分类、联系方式、官网备注和底部备案信息。

每个页面必须包含 canonical、清晰 H1、正文摘要、内部链接和更新信号。

产品、服务、FAQ、文章等内容必须同时存在于正文和对应 Schema 中。

当系统没有对应数据时，显示真实空状态，不要编造内容。

公开页面不要输出“后台设置、系统配置、模板编号、AI 友好、本模块读取、数据来源”等建站说明；空状态使用“暂无内容、暂无联系方式、内容更新后展示”等中性官网文案。
```

## 13. 官网模板验收清单

上线前检查：

- 首页是否直接说明品牌做什么；
- H1 是否清晰且唯一；
- 核心答案是否在 HTML 正文中；
- 是否删除演示客户、演示指标、假案例；
- 公司介绍是否来自后台配置或真实资料；
- 产品 / 服务介绍是否来自后台配置或真实资料；
- 文章是否使用真实系统数据；
- FAQ 是否覆盖真实用户问题；
- 联系方式是否来自后台配置；
- 页脚是否展示官网备注、备案、版权；
- Schema 是否与正文一致；
- sitemap 是否包含责任页面；
- canonical 是否正确；
- 页面是否有发布时间或更新时间信号；
- JS 关闭后，核心正文是否仍可读取；
- 空数据状态是否真实，不编造内容；
- 前台是否没有暴露“后台、系统配置、模板编号、数据来源、本模块读取”等系统性提示文字；
- 空状态是否使用访客可理解的中性文案，而不是管理端配置提示；
- 模板是否能被复用为不同站点，而不是写死某个项目文案；
- 是否存在访问日志、抓取日志或后续测量方案。

## 14. AI 友好官网模板分级

### 14.1 合格模板

满足：

- 有完整首页、文章、分类、关于、联系页面；
- 使用系统真实数据；
- 页面有正确标题、描述、canonical；
- 首页没有虚构演示信息；
- 文章内容可被直接抓取。

### 14.2 标准模板

在合格模板基础上增加：

- 首页具备品牌介绍、产品服务、解决方案、文章、联系模块；
- 输出 `WebSite`、`Organization`、`Article` 等基础 Schema；
- sitemap 覆盖核心页面；
- 页脚完整展示联系、备注、备案、版权；
- FAQ 或问题模块能覆盖真实用户提问。

### 14.3 AI 友好优秀模板

在标准模板基础上增加：

- 每个核心模块都有可引用正文；
- FAQ 与 Schema 完全一致；
- 产品、服务、文章、分类、案例之间有清晰内链；
- 页面更新时间清晰；
- 支持问题覆盖、访问日志、抓取监测和周期复测；
- 无图片正文替代、无伪数据、无只对人类可见但 AI 不易抓取的核心信息。

## 15. 后续产品化建议

为了让官网模板真正达到 AI 友好标准，建议后续补充以下后台能力：

- 公司介绍配置；
- 产品 / 服务介绍配置；
- FAQ / 问题库配置；
- 官网案例或证据库配置；
- sitemap 可视化检查；
- 页面抓取与 AI 引用监测；
- 模板模块保存与复用；
- 模板空状态审查；
- 页面结构化数据校验。

这些能力不是一次性都必须上线，但模板设计时应提前预留字段、模块位置和扩展边界。
